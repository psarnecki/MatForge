# 00. Overview

## 1. Purpose

A web application in which a grappling athlete (BJJ, wrestling, judo, sambo) records training, sparring rounds, and competitions, and receives **analysis of progress**: where they win, where they lose, which techniques they finish with, which they get caught by, and how this changes over time.

The core of the thesis is the **analytics module** (`03-analytics.md`). Everything else exists to feed it with clean, consistent data.

## 2. Users

One role: **athlete**. Each athlete sees only their own data. There is no admin role and no admin panel (see D-02).

| SHOULD | Thesis material and a short root README: ERD and architecture diagrams, endpoint list, run instructions (T21) |
| COULD | Everything in `08-optional.md` (CI, dark scheme, Polish UI, ...) |

**Cut order when behind schedule (first to cut first):** everything in `08-optional.md` → thesis material (T21) → delete account → demo data. All MUST features come from the thesis concept and should stay.

### Out of scope

Admin panel, e-mail sending (confirmation, password reset), social features, coach accounts, payments, native mobile apps, offline mode, import/export, tracking of individual techniques drilled in class, scoring details (points/advantages) of rounds, and the concept's further-development items (machine learning, event diary, PDF reports, technical tags on sessions).

Every decision below was made to keep implementation simple and fast. Change any of them by editing this table first.

| D-35 | Rules that make a request invalid (`400`) and need the database are FluentValidation validators that inject `AppDbContext` (one `AddScoped<IValidator<XxxRequest>, XxxValidator>()` line each; the existing validation filter runs them). Conflicts that depend on the current state of the data (`409`: duplicate club name, duplicate measurement date, club or competition in use) stay in the services. **Consequences:** validator tests that need the database live in `MatForge.IntegrationTests` and call the validator directly against the container database (not over HTTP); pure unit tests only for rules without the database; a validator loads the IDs it checks once, not one query per item; async rules require `ValidateAsync` (the filter already uses it); with `[ApiController]` a DataAnnotations failure returns `400` before the filter runs, so such a response shows only the DataAnnotations errors (known limitation). | **Context:** several rules depend on the database: I-02 (belts); I-01, I-05, I-09, I-10, I-11 (sessions); I-01, I-10 (competitions and fights). I-03 and I-04 need only the request, so they are checked without the database. Sessions and competitions share rules (format belongs to the discipline, technique offered in the discipline). **Options:** A) validators that query the database; B) the same rules inside the services, throwing `BadRequestException`. **Why A:** one place and one error format for every invalid-request rule, with field keys such as `belts[0].degree` produced by the existing camelCase helper; services stay short and only do the use case; the shared rules of sessions and competitions are written once. B would need a helper class shared by the services for the same rules, which in practice is A under another name. **VetClinic / MartialHub comparison:** VetClinic (MVC, EF Core) has no FluentValidation; DataAnnotations on DTOs plus `ModelState.IsValid` in controllers, and the database rules live in services that return `bool`/`null` or throw `UnauthorizedAccessException`/`KeyNotFoundException` (`AnimalService.DeleteAnimalAsync`, `MedicationService.DeleteMedicationAsync`, `VisitUpdateService`), which controllers turn into `TempData` messages, `Forbid()` or `NotFound()`; referenced IDs are not checked before saving (select lists and foreign keys only); tests are unit tests with Moq and EF Core InMemory. | D-37 | Mapperly mappers are `static partial` classes and are not registered in dependency injection. Request-to-entity mappings keep Mapperly's default and check both sides: every target field a mapping does not fill is named with its own `[MapperIgnoreTarget]`, and every request field must reach the entity. Every `ToDto` method carries `[MapperRequiredMapping(RequiredMappingStrategy.Target)]`, so a DTO may leave out entity fields. Mapperly's unmapped-field diagnostics (RMG012 for a target, RMG020 for a source) fail the build through `TreatWarningsAsErrors`. On `PUT` the service copies the fields and rebuilds child lists by hand. Package: `Riok.Mapperly` 4.3.1 (stable). | **Principle:** the author wants errors caught at compile time rather than at runtime. This recurs throughout the project (strict TypeScript, warnings as errors, explicit ignores). A static mapper has nothing to register, so a forgotten registration cannot fail at runtime, and a field that is not mapped breaks the build until someone decides how to map it. **Why the two directions differ:** an unfilled target field silently stays at its default value, and a request field the entity does not receive is a value from the client that is silently thrown away, so both break the build. A DTO that leaves out an entity field is a design decision, and listing every such field (14 attributes for the session mappings alone) would add noise and protect little. The strictness is the default and the relaxation is per method, so a `ToDto` that forgets the attribute fails loudly at build time instead of losing the check silently. **Why static:** the mappers have no dependencies, so dependency injection would add wiring and nothing else. It makes sense only when a mapper needs an injected service or configuration. **Why `PUT` by hand:** a Mapperly update mapping would need about as many ignore lines as there are fields to copy. **VetClinic comparison:** VetClinic registers its mappers in dependency injection (13 `AddScoped` lines, injected into the services), although none of them needs an injected service and its tests create them with `new()`. The generated mapping code is the same; MatForge drops the wiring. |

## 5. Glossary

| Term | Meaning |
|---|---|
| Session | One training event on a given date. Kind = Grappling or Other. |
| Round | One sparring round inside a grappling session. |
| Finish | A round or fight decided by one decisive action: a submission, a takedown or throw, or a pin (D-20). |
| Finish for / against | Finish by the athlete (Win) / by the opponent (Loss). |
| Technique | A finishing action from the dictionary (e.g. Rear Naked Choke, Double Leg, Uchi Mata). |
| Category | Group of techniques (Choke, Arm Lock, Leg Lock, Takedown, Throw, Pin, ...). Each category is offered in chosen disciplines (D-29). |
| Position | Where the finish was applied (Mount, Back Control, Saddle, ...). See D-07. Each position is offered in chosen disciplines (D-33). |
| Format | Variant of a discipline (BJJ Gi / No-Gi, Freestyle / Greco-Roman, ...). |
| Character | Dominant nature of a grappling session (Technique, Drilling, Sparring, ...). |
| Period | Inclusive date range `[from, to]` used by analytics. |
| Share | A fraction 0..1 (UI shows percent). |
