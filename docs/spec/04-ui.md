# 04. UI

## 1. Stack

Vite + React + TypeScript (strict) + React Router + **Recharts**. Plain CSS, no UI library. The technologies are the ones named in the concept plus the minimum needed to build and route a React app.

| Need | Solution |
|---|---|
| Components | Own small components in `src/components` (Button, Field, Select, Dialog, Toast, Tabs, ...), styled with CSS and the design tokens |
| Forms | Controlled inputs with `useState`; simple input checks only, the server is the authority |
| Calendar | Own month-grid component (`MonthCalendar`) with session markers; plain `Date` handling |
| Charts | Recharts (line and bar charts), colors from the tokens |
| Server data | `fetch` through one `apiFetch` helper; each feature has small hooks (`useSessions`, ...) built on `useState` and `useEffect` |
| API types | DTO types written by hand in `src/types.ts`, mirroring the backend DTOs |
| HTTP | One `apiFetch` wrapper: same-origin `/api`, `credentials: "include"`, parses ProblemDetails into typed errors, redirects to login on `401` |
| Fonts | `@fontsource/barlow` and `@fontsource/barlow-condensed` (bundled; no CDN, works offline at the defense) |
| Texts | All UI texts in one file, `src/texts.ts` (a plain object; insight sentences are small functions of `rule` + `params`). No text literals in components, no i18n library |
| Icons | A few inline SVG icons (navigation, actions); no icon library |

Folder layout: `src/features/{auth,profile,sessions,competitions,analytics,goals,materials,measurements}`, `src/components` (shared), `src/api`, `src/styles` (all styling: `tokens.css`, `base.css`, `components.css`, and one CSS file per feature), `src/lib`.

## 2. Visual direction

**Brief (from the author):** modern combat-sports look in black, red, and white, inspired by ufc.com and adcombat.com: a **light content area under a black top bar**, as on both reference sites (chosen from mockups). The brief wins over generic taste. Reference screenshots go to `docs/design/` and are the first thing an agent looks at before building a screen. The five approved mockups (plain HTML files: dashboard, log training on a phone, training calendar on a phone, competition on a phone, goals) are in `docs/design/`; open them in a browser or read their CSS. The mockups load fonts from Google Fonts and use inline styles for convenience; the app bundles the fonts with `@fontsource` and keeps all styling in `src/styles/`. Where a mockup and this spec disagree, the spec wins.

**Subject and job:** a tool an athlete opens on a phone right after training, to log what happened in under a minute, and on a laptop to read their numbers. Tone: serious, athletic, direct.

### Reference notes (read from the CSS of ufc.com and adcombat.com)

- ufc.com: brand red `#d20a0a`; blacks `#000000` and `#191919`; dark grey `#333333`; greys `#ABADB1`, `#D5D6D8`, `#EEEEEF`, `#F6F7F7`. Titles in a condensed bold face (Klavika Condensed / UFC Sans Condensed), body in UFC Sans / DIN 2014. These fonts are proprietary and are not used.
- adcombat.com: Montserrat, red-orange accent `#e03b25`, dark red `#ac1f1a`, footer `#191919` / `#222222`. Not used: we keep a single red (the UFC one) and avoid wide geometric fonts.
- Both sites use light content areas (`#f2f2f2` / `#f3f3f3`) under a black header and footer. The app follows this: light content, black chrome. A dark color scheme is a COULD; it is cheap only if no component hard-codes a color (tokens only).

### Tokens (single source: `src/styles/tokens.css`)

Components never hard-code colors; they use these tokens (exposed as CSS variables), so a dark scheme can be added later without touching components. Recharts colors come from the same variables (pass `var(--brand)` and the like to the chart props; if a chart element does not accept CSS variables, read them once in `src/lib/chartColors.ts`).

| Token | Light (MVP) | Dark (COULD) | Use |
|---|---|---|---|
| `bg` | `#F2F2F2` | `#000000` | page background |
| `surface` | `#FFFFFF` | `#191919` | panels, inputs |
| `chrome` | `#000000` | `#000000` | top bar and bottom tab bar (black in both schemes) |
| `chromeText` | `#FFFFFF` (inactive links `#ABADB1`) | same | text on chrome |
| `line` | `#D5D6D8` | `#333333` | 1px borders and dividers |
| `text` | `#191919` | `#FFFFFF` | primary text |
| `textMuted` | `#585B63` | `#ABADB1` | secondary text (at least 4.5:1) |
| `brand` | `#D20A0A` | `#D20A0A` | primary buttons, active navigation underline, losses, large numerals. On light it also works as text (about 5.5:1); on dark only for large text (about 3.8:1) |
| `brandText` | `#D20A0A` | `#FF5A5A` | small red text and links |
| `win` | `#1F7A4A` | `#3FA66B` | wins in charts and badges |
| `loss` | `#D20A0A` | `#D20A0A` | losses in charts and badges |
| `draw` | `#6B6E75` | `#8A8A8A` | draws |

Implementation: all CSS lives in `src/styles/`; the variables are in `src/styles/tokens.css` (light values on `:root`; a dark set can later be added under `[data-theme="dark"]`); border radius 2-4 px; no shadows (use 1px `line` borders).

Typography:
- Headings: **Barlow Condensed**, weight 700, uppercase, tight tracking. Uppercase is reserved for headings and the main navigation.
- Body, forms, tables: **Barlow**, 400/500/600, sentence case.
- Why these fonts: they are free faces with the proportions of the DIN-style fonts used on ufc.com (Barlow Condensed for titles, Barlow for text). Montserrat is intentionally not used.
- Numbers in stat blocks and tables use tabular figures (`font-variant-numeric: tabular-nums`).
- Line length under 80 characters; type scale (px): 12 / 14 / 16 / 20 / 28 / 40 / 64.

### The one memorable element

The **record strip** on the dashboard: wins, losses, and draws as huge condensed numerals (72 px, ink / brand / grey) with a thin segmented bar under them. Everything else stays quiet. Do not add a second hero treatment elsewhere.

### What makes it look generated (do not do this)

- Identical rounded cards stacked everywhere, nested cards, one radius and one soft shadow on everything.
- Gradients, glassmorphism, glow, decorative blobs.
- Emoji or decorative icons in headings or empty states. Use plain inline SVG icons only where they carry meaning (navigation, actions).
- Small ALL-CAPS labels above every section, middle-dot meta strings, `→` on buttons, spaced em-dashes in labels, numbered markers (01/02/03) on content that is not a sequence.
- Fade-and-slide entrance animations on every block, hover lift on every card. Motion only answers a user action (opening a drawer, saving, deleting).
- Purple/blue accents, default framework blues, Inter or system-default fonts.
- Using a card where plain spacing and a divider line is enough. Group by whitespace and `line` borders first.

## 3. Layout and navigation

- **Desktop (≥ 992 px):** black top bar (logo left, text links, user name right; the active link has a 3 px brand underline), content area max width 1200 px, 32 px gutters.
- **Tablet (576-991 px):** the same top bar with horizontally scrollable links.
- **Phone (< 576 px, minimum supported width 360 px):** bottom tab bar with 5 items (Dashboard, Training, Competitions, Goals, More). "More" opens Library, Body, Profile. Primary actions use a sticky bottom button or a floating action button in thumb reach. Touch targets ≥ 44 px.
- Every page has one `h1`. Visible keyboard focus. Respect `prefers-reduced-motion`.
- Routes: `/login`, `/register`, `/` (Dashboard), `/training`, `/training/new`, `/training/:id`, `/competitions`, `/competitions/new`, `/competitions/:id`, `/goals`, `/library`, `/body`, `/profile`.

## 4. Screens

### 4.1 Login / Register
Single column, centered form, no marketing copy. Register: email, password, first name, last name (the chain in `02-api.md`, section 2). Errors from ProblemDetails are shown under the fields; password errors come from the server (the default Identity rules) and are shown as returned.

### 4.2 Dashboard (`/`)
- **Period selector:** presets This month, Last 30 days, Last 90 days, This year, All time (the client sends no dates; the server starts at the user's earliest data), plus a custom range. Selection kept in the URL query. Default: Last 90 days.
- **Filters:** one shared control (discipline and format, both optional) next to the period selector. It applies to the Sparring, Competitions, and Insights sections; Overview ignores it.
- Tabs (on phone) or sections (on desktop): **Overview**, **Sparring**, **Competitions**, **Insights**.
- Overview: sessions count, hours, average per week; weekly bar chart; distribution by discipline/format/club/character as horizontal bars (not pie charts).
- Sparring: the **record strip**, win-rate trend line (buckets from the API), top finishes for and against (bar lists by technique, category, position).
- Competitions: record strip, medals, methods of winning and losing, timeline table (competition, date, place, fights, record), win rate vs previous period.
- Insights: Strengths and Weaknesses as two plain lists; Trend and Info below. Each item is a sentence built from `rule` + `params` in `texts.ts`. `InsufficientData` shows what is missing ("At least 10 sparring rounds are needed; you have 6") and links to adding training.
- Empty periods show a one-sentence instruction and a button to log a session.

### 4.3 Training (`/training`)
- Month calendar (own `MonthCalendar` component); days with sessions show a small marker, with a count when more than one. Clicking a day lists its sessions under the calendar (on desktop: right panel). Month navigation loads `GET /api/sessions?from&to` for the visible month.
- Primary action: **Log training**.

### 4.4 Session form (`/training/new`, `/training/:id`)
Mobile-first, one column, sections separated by whitespace:
1. Kind toggle: Grappling / Other. Date (default today), duration (minutes, quick chips 60 / 90 / 120 plus free input), feeling 1-5 (segmented control).
2. Grappling: discipline → format (filtered by discipline) → character → club (user's clubs plus "Other"). Defaults remembered from the last session (kept in `localStorage`).
3. Other: activity type.
4. **Rounds, quick entry (shown only when the selected character allows rounds):** three large buttons **Win / Loss / Draw** append a round chip. A live summary shows "5 rounds: 3 W, 1 L, 1 D". Tapping a chip opens a bottom sheet / popover to set technique (a native select grouped by category with `<optgroup>`), position (select), notes, or remove the round. Win and Loss chips show a small marker when a technique is set. Technique and position fields are hidden for Draw.
5. Notes. **Save** (sticky on phone). After saving, return to the calendar on the saved month.
Server validation errors map to fields.

### 4.5 Competitions (`/competitions`)
List sorted by date (table on desktop, rows on phone) with place and record. Detail/form: competition fields, the result as three quick buttons (gold, silver, bronze = place 1, 2, 3) plus a number field for any other place and a short text note, then a fights list: result (Win, Loss, Draw), method (hidden for Draw; technique appears only for Submission), duration (mm:ss input stored as seconds), opponent, notes. On phone each fight is a compact stacked row.

### 4.6 Goals (`/goals`)
List of active goals, each with title, progress bar, "12 / 20", days remaining, and a state badge. Create/edit dialog with fields depending on type. Manual goals have a progress slider. Archive action. Archived goals behind a toggle.

### 4.7 Library (`/library`)
Filter chips for status and category. Rows show title, source, category, status. Status changes with a single tap (menu). Add dialog: paste URL, title, category. The source icon comes from the server's detection.

### 4.8 Body (`/body`)
Line chart (toggle weight / height / body fat), list of entries below, add/edit dialog. One entry per date.

### 4.9 Profile (`/profile`)
Name; clubs (add, rename, delete, with the 409 message shown); belts (one select per discipline, "none" allowed, plus a stripes / degree selector); delete account (confirmation dialog requiring the user to type their e-mail).

## 5. Copy rules

- Sentence case, plain verbs, no filler. Buttons say what they do: "Save session", "Delete competition". The same action keeps the same name in the button, the toast, and the history.
- Errors say what happened and how to fix it; they never apologize. Empty states tell the user what to do next.
- Neutral terms: "round", "finish", "submission". Avoid slang.

## 6. Interaction rules

- Every mutation shows a loading state on its button and a toast on success or failure; lists are refetched after the change.
- Destructive actions ask for confirmation.
- No full-page spinners after first load: show skeletons for charts.
- Charts: no gridlines clutter, thin lines, tooltips with exact numbers, colors per `win` / `loss` / `draw` tokens consistently across the app.

## 7. Design review loop

While building each screen, look at it at 390 px and 1440 px and compare it with `docs/design/`. In T19 do the full loop for every screen:

1. Capture screenshots at **390 px** and **1440 px** (Playwright script or manually).
2. Compare with `docs/design/` and the "do not do this" list above.
3. Fix, then capture again. Screenshots are optional; if you keep them, save them in `docs/design/shots/`.
